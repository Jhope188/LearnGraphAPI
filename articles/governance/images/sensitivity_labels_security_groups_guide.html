Sensitivity labels for Entra security groups

Setup guide, configuration walkthrough, and gotchas — based on official MS Learn documentation

1
Entra ID P1 license
Required

At least one active Microsoft Entra ID P1 license must exist in the tenant. This is satisfied by M365 E3, M365 E5, or Business Premium. E5 is not required for the base feature.

✓M365 E3 — includes Entra P1
✓M365 E5 — includes Entra P1 and P2
✓Business Premium — includes Entra P1
✗M365 Business Standard — Entra ID Free only, not supported
2
EnableMIPLabels set to True in Group.Security
Required

Cloud security groups use the Group.Security directory settings template. This is a separate template from Group.Unified used for M365 groups. Even if M365 group labels are already working, you must create this setting separately.

Already done for conditionalaccess.tech: Setting ID 48e62f10-5d35-42c6-b9a9-015511fa80d2 was created with EnableMIPLabels: True and AllowToAddGuests: True.
PowerShell — create if not exists
$params = @{ templateId = "d209f6fa-3839-4d70-b83f-60b1c64d0e8f" values = @( @{ name = "AllowToAddGuests"; value = "True" } @{ name = "EnableMIPLabels"; value = "True" } ) } New-MgBetaDirectorySetting -BodyParameter $params
PowerShell — verify
(Get-MgBetaDirectorySetting | Where-Object { $_.DisplayName -eq "Group.Security" }).Values
3
Labels published in Purview with Groups & Sites scope
Required

Sensitivity labels must be published in Microsoft Purview with the Groups & Sites scope enabled. The same labels used for M365 groups will apply to security groups — no separate label configuration is required.

In Purview: Information Protection → Labels → Edit → Scope → check Groups & sites. Then publish via a label policy scoped to the relevant users or groups.

Important: The label policy must be scoped to include the user who will assign labels to groups. If the user isn't in scope of the policy, the label dropdown won't appear even if all other prereqs are met.
4
Labels synchronized to Entra ID
Required

Run Execute-AzureADLabelSync from Security & Compliance PowerShell to synchronize labels to Entra ID. This cmdlet is not available in the Graph PowerShell SDK.

Connect-IPPSSession Execute-AzureADLabelSync
Allow up to 24 hours after synchronization for labels to become available in the Entra admin center group dropdown. If the label was recently published, this is the most common reason for the dropdown appearing empty.
5
Group type and membership requirements
Constraints

Labels are only supported on specific group types. Check before attempting to apply.

✓Cloud security groups — assigned membership type
✗Dynamic membership groups — not supported in this release
✗On-premises synced groups — not supported
✗Mail-enabled security groups — not supported
✗Groups with nested child groups — must remove children before labelling
1. Open the label in Purview
Microsoft Purview portal → Information Protection → Sensitivity Labels → select your label → Edit label. For a Restricted label this walkthrough covers the Groups & sites page specifically.
2. Scope — check Groups & sites
On the Scope page, check Groups & sites. This enables the container-level settings pages. Files, Emails should also remain checked for full label coverage. Meetings is optional but recommended for Restricted labels for consistency across content types.
3. Groups & sites — enable protection settings
On the Groups & sites page, check Privacy and external user access. This is the setting that controls guest enforcement on both M365 groups and Entra security groups. Without this checked, the label has no enforcement at the container level even if Groups & sites scope is enabled.
4. Privacy and external user access settings
Set Privacy to Private for Restricted labels. Leave the External user access checkbox unchecked to block guests. The checkbox reads: "Let Microsoft 365 Group and Entra Security Groups owners add people outside your organization to the group as guests." Unchecked = no guests permitted on labeled groups.
5. Private teams discoverability and shared channel controls
Uncheck Allow users to discover private teams with this label applied. For shared channels check: Internal only, Same label only, and Private teams only. All three stack additively for maximum restriction on a Restricted label.
6. Save and publish
Save the label. If this is a new label, publish it via a label policy in Purview. Then run Execute-AzureADLabelSync to push the updated configuration to Entra ID. Allow up to 24 hours for changes to be available in the group Properties dropdown.

⚠️ Labels are immutable — by design, not preview limitation

Once a sensitivity label is applied to a security group it cannot be changed or removed. This is an architectural decision, not a temporary preview constraint. The MS Learn page notes this may change before GA once Microsoft builds full membership re-validation logic — but do not assume it will.

If you apply the wrong label: create a new group with the correct label and re-add members. There is no in-place remediation path.

Client advisory: Define your label taxonomy before applying labels to any production security group. The portal shows a Remove button for admins but this is the high-privilege bypass — the warning banner is accurate.
🚨 High-privilege bypass — enforcement is not universal

During preview, the following roles and application permissions bypass label policy enforcement entirely when adding members. This is confirmed in the MS Learn Known Limitations section and was demonstrated live in this tenant.

This means any automation, service principal, or privileged admin can bypass enforcement today. Demo to non-privileged users only to show the enforcement working correctly.

⚠️ Existing members are not evicted when a label is applied

If a group already contains guests and you apply a label with guest-blocking policy, those existing guests remain. The label validates new additions only — it does not retroactively enforce against current membership.

The MS Learn doc notes: "if you change a label from allowing to blocking guest access, guests already in those groups remain until an owner or admin removes them."

Remediation: Audit existing members before applying a label. Remove conflicting members first, then apply the label. The portal will fail the save if a membership conflict exists at label assignment time.

ℹ️ Group.Security and Group.Unified are separate — both needed

Enabling labels for M365 groups (Group.Unified template) does not enable them for security groups. The two templates are independent and both require EnableMIPLabels: True. This is the most common reason clients see labels working on M365 groups but not appearing on Security group Properties pages.

ℹ️ Nesting requires compatible labels on all child groups

You cannot apply a label to a security group that contains nested child groups. The sequence is: remove all nested groups → apply label to parent → label each child group with an equally or more restrictive label → add children back.

You cannot nest an unlabeled group under a labeled parent, and you cannot nest a child with a less restrictive label than the parent.

ℹ️ Label policy changes do not update existing labeled groups automatically

If you change a published label's Groups & sites settings in Purview, those changes do not automatically apply to groups already labeled. Microsoft recommends against changing group settings on published labels that are already in use.

If you must change settings, use the PowerShell reassignment script from the Microsoft Graph samples repo to manually push updates to affected groups.
