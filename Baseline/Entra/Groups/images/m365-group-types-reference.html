SecurityEnabled: The Portal Trap (observed behaviour)

When created in the M365 Admin Center, securityEnabled is set to false — the group cannot be used for group-based licensing. When created in the Entra Admin Center or via Graph API, securityEnabled can be set to true — licensing works. Fix after the fact with Update-MgGroup -SecurityEnabled:$True. The UI does not expose this property.

Source note: This portal-specific difference is widely observed but not explicitly documented on Microsoft Learn. Graph API docs default M365 Group examples to securityEnabled: false. Verify in your own tenant.

DDG
Dynamic Distribution Group
Exchange-native · Recipient filter resolved at send time

Like a distribution group but membership is determined by Exchange recipient filters (department, office, etc.) evaluated at the moment each message is sent. Not stored continuously like Entra dynamic groups — the membership list is generated on demand.

Key Difference from Entra Dynamic Groups

Entra dynamic groups maintain a continuously evaluated, stored membership list. Dynamic Distribution Groups resolve the list fresh at every send. This means a DDG doesn't reflect real-time directory changes the same way — there is inherent latency between an attribute change and the next message send.

Hidden Governance Gap

When an Entra Security Group is added to a SharePoint Group, the site owner sees the group name but cannot see who is inside it. This creates a visibility gap — the person responsible for the site may not know who actually has access.

What Happens When You Create Groups From Different Portals

The same "group" created from different admin centers can have different properties, different side effects, and different capabilities. This is the single biggest source of confusion in M365 group management.

Entra Admin Center (entra.microsoft.com)
Security Group M365 Group Distribution Group Mail-Enabled SG Dynamic Distribution Group
The primary portal for identity and access management. When you create an M365 Group here, securityEnabled is set to true, which means the group can be used for group-based licensing, Conditional Access targeting, and application assignment. This is the recommended creation path for M365 Groups you plan to use for both collaboration and access control.
What gets provisioned

Security Group: Entra directory object only. No mailbox, no SharePoint site, no additional resources. Optionally set as role-assignable or dynamic at creation time.

M365 Group: Entra directory object plus Exchange shared mailbox, SharePoint team site, Planner, OneNote, and Calendar. All provisioned automatically. securityEnabled: true.

Exclusive capabilities here

Dynamic membership rules (user or device attribute-based), role-assignable flag, PIM enrollment, sensitivity labels, expiration policies. These are Entra-native features not available from Exchange.

Microsoft 365 Admin Center (admin.microsoft.com)
Security Group M365 Group Distribution Group Mail-Enabled SG Dynamic Distribution Group
The broadest creation surface for non-Exchange-specific groups. However, M365 Groups created here behave differently from those created in Entra.
The securityEnabled Trap (observed behaviour)

When you create an M365 Group in the M365 Admin Center, securityEnabled is set to false. This means the group cannot be used for group-based licensing until you manually update the property: Update-MgGroup -GroupId $id -SecurityEnabled:$True. The UI does not expose this property.

Note: This portal-specific behaviour is widely reported by MVPs and community testing. Microsoft Learn does not explicitly document the per-portal difference.

What gets provisioned

Security Group: Same as Entra — directory object only. Can also opt into mail-enabling here (creating an MESG) at creation time.

M365 Group: Same resources as Entra (mailbox, SharePoint, etc.) but with securityEnabled: false.

Distribution Group: Exchange recipient object. No Entra access control capability.

Mail-Enabled Security Group: Must be mail-enabled at creation — cannot be added later.

Exchange Admin Center (admin.exchange.microsoft.com)
Distribution Group Dynamic Distribution Group M365 Group Mail-Enabled SG Security Group (non-mail)
The mail-centric portal. This is the only place you can create Dynamic Distribution Groups. Also the primary management interface for Distribution Groups and Mail-Enabled Security Groups.
Exchange-specific management features

Delivery restrictions, message moderation, sender limitations, approval workflows, external mail reception toggles, MailTips — all Exchange-native features not available in the Entra portal.

Distribution Lists and MESGs are Exchange-managed only

Even though these objects appear in the Entra directory, they can only be managed from the Exchange Admin Center, M365 Admin Center, or PowerShell. The Entra admin center shows them as read-only.

Microsoft Teams / Outlook
M365 Group (implicitly)
When a user creates a new Team in Microsoft Teams, an M365 Group is automatically created in the background — including the SharePoint site, mailbox, and all connected resources. The group's resourceProvisioningOptions attribute gets set to ["Team"]. Similarly, creating an Outlook group creates an M365 Group with a mailbox focus.
Governance implication

Because M365 Groups can be created by any licensed user through Teams or Outlook (by default), this is the primary driver of group sprawl. Restrict creation via Entra group settings (EnableGroupCreation: false) and whitelist a security group of allowed creators.

Graph API / PowerShell (New-MgGroup)
All types
Maximum flexibility. Every property — securityEnabled, mailEnabled, groupTypes, isAssignableToRole, membershipRule — is explicitly set by you. No portal defaults to worry about. This is the only creation method where you have full control over the object's shape from the start.
Graph property combinations define the type

groupTypes: ["Unified"] + mailEnabled: true = M365 Group

groupTypes: [] + securityEnabled: true + mailEnabled: false = Security Group

groupTypes: [] + mailEnabled: true + securityEnabled: false = Distribution Group

groupTypes: [] + mailEnabled: true + securityEnabled: true = Mail-Enabled Security Group

Token Group Membership Limit — SharePoint

A user can be a direct or transitive member of up to 2,048 security groups before authentication tokens become oversized. Exceeding this produces unpredictable authentication and search results in SharePoint Online — a silent failure mode in large enterprises with deep nesting. This is an Entra/token constraint, not a SharePoint group limit.

Key Gotchas & Things That Catch People

1. M365 Group securityEnabled varies by portal (observed behaviour, not formally documented)

Created in M365 Admin Center → securityEnabled: false → cannot use for licensing.
Created in Entra Admin Center → securityEnabled: true → licensing works.
Created via Graph/PowerShell → you set it explicitly.
Fix: Update-MgGroup -GroupId $id -SecurityEnabled:$True

Source note: Microsoft Learn's Graph API examples default M365 Groups to securityEnabled: false, and the licensing docs confirm the requirement. The portal-specific difference is widely observed (MVP blogs, community testing) but not explicitly stated in a Microsoft Learn article. Verify in your own tenant.

2. Role-assignable is immutable

The isAssignableToRole flag must be set at group creation. You cannot make an existing group role-assignable, and you cannot remove the flag once set. Plan ahead — the 500-group tenant limit makes this even more important to get right the first time.

3. Mail-enabling is a one-way, creation-time decision

You cannot convert an existing cloud-only security group into a mail-enabled security group after creation. The mail-enable option is only available at creation time in the Exchange Admin Center. On-premises mail-enabled SGs synced via Entra Connect are supported but must be managed on-premises.

4. Licenses cannot be assigned through nested groups

Even though nesting is supported for Security Groups, group-based licensing does not traverse nested memberships. Only direct members of the licensed group receive the assignment. This is one of the few M365 services where transitive group membership is explicitly not supported.

5. Dynamic groups ≠ Dynamic Distribution Groups

Entra dynamic groups maintain a continuously stored membership list updated in near-real-time. Exchange Dynamic Distribution Groups resolve membership at send time via recipient filters. They are completely separate systems with different rule syntaxes, different evaluation timing, and different management surfaces.

6. Distribution Groups and MESGs are read-only in Entra

They appear in the Entra directory but can only be managed from the Exchange Admin Center, M365 Admin Center, or PowerShell. The Entra portal will not let you edit membership.

7. Teams creation = M365 Group sprawl

Every Team created by end users automatically creates an M365 Group with all connected resources. Without restricting group creation via EnableGroupCreation: false in Entra group settings, every licensed user is a group creator by default.

8. Dynamic group privilege escalation risk

If a dynamic security group is assigned an Entra directory role, any admin who can modify the dynamic membership rule could add themselves to the rule and indirectly elevate their own privileges. Microsoft explicitly calls this out as an attack path — it is why role-assignable groups block dynamic membership entirely. The attack vector is the rule itself, not general group membership modification.

9. Only M365 Groups have GA restore — Security Group restore is still in preview

Distribution Groups and Mail-Enabled Security Groups cannot be soft-deleted and restored. If you delete one, it is gone. M365 Groups get a 30-day soft-delete window (GA). Cloud security group restore is available but still in preview as of mid-2026, and only in public clouds. EDU tenants and some classic web part scenarios are excluded.

10. SharePoint Groups are invisible to Entra

SharePoint site permission groups (Owners/Members/Visitors) are not Entra objects. When an Entra Security Group is added to a SharePoint Group, the site owner sees the group name but cannot see its members — a governance blind spot that Inforcer's configuration visibility helps surface.

11. Nested group access varies by M365 workload

Transitive security group membership is evaluated in SharePoint Online (nested SG members do inherit permissions) and in Conditional Access scope. It is not evaluated for group-based licensing (direct members only) or for M365 Group shared mailbox access. Teams channel behaviour is inconsistent and should be verified per scenario. Do not assume transitive inheritance is uniform across M365 services.
