The Foundation
Every method
talks to a CSP
A Configuration Service Provider (CSP) is the Windows OS-level framework that receives and applies settings from any MDM. It's the engine — not an admin interface.
CSP = the engine Sits on the Windows device. Intercepts MDM configs, compares to current state, applies changes via Registry or OS feature. Every other method — OMA-URI, Settings Catalog, Templates — ultimately calls a CSP path.
OMA-URI = manual CSP path You write the path yourself: ./Device/Vendor/MSFT/Policy/Config/...
Maximum power, zero guardrails.
Settings Catalog = searchable UI over CSPs The same CSP paths, but Microsoft wraps them in a searchable interface. Better reporting, conflict detection, and cross-platform support.

Custom Profile
OMA-URI:
The Escape Hatch
When a setting doesn't exist in the Settings Catalog UI yet, you go manual. You write the exact CSP path, data type, and value yourself.
When to use it Only when the setting genuinely doesn't exist in Settings Catalog. Microsoft is actively restricting OMA-URI to settings absent from the catalog.
Risks to know No conflict detection. Basic pass/fail reporting only. Silent misconfigurations are easy — a typo in the path silently fails.
Path format ./Device/Vendor/MSFT/Policy/Config/[Area]/[Setting]
Always verify scope (Device vs User) in the Microsoft CSP reference before deploying.

Settings Catalog
Microsoft's
Unified Standard
The Settings Catalog is now the default for all new Intune policies. 18,000+ settings across Windows, macOS, iOS, and Android — searchable by name, keyword, or CSP path. Last updated 5/27/2026.
Why it replaced Templates Administrative Templates are retired for new creation (Dec 2024). Settings Catalog contains every ADMX setting plus thousands more — with better conflict reporting and cross-platform parity.
DDM settings live here too Apple Declarative Device Management settings surface inside the Settings Catalog under the DDM category — not a separate interface. Look for "Declarative Device Management (DDM)" in the left nav.

Declarative Device Management
DDM: Device-Driven
Management
Traditional MDM is server-driven — Intune sends commands, polls for status. DDM flips this: the device declares its desired state and self-enforces it, even when offline.
MDM (old model) Server sends command → device executes → server polls for result. Race conditions, unreliable status, offline gaps.
DDM (new model) Intune declares "target OS = 15.5 by Friday" → device autonomously manages download, install, and progress reporting. Works offline.
⚠️ This is urgent for Apple admins Apple deprecated legacy MDM update commands at WWDC 2025. iOS/iPadOS/macOS 26 will remove them entirely. Migrate to DDM before OS 26 ships (autumn 2026).

What's Deprecated & When
The Migration
Timeline
Aug 2024
macOS Endpoint Protection & System Extensions templates deprecated. Migrate to Settings Catalog (FileVault, Firewall, Gatekeeper payloads).
Dec 2024
Administrative Templates retired for new creation. Cannot create new ADMX-based profiles. All settings exist in Settings Catalog. Existing policies still work.
Jun 2025
Apple WWDC: MDM software update commands deprecated in OS 26. DDM is now required for Apple update management.
Autumn 2026
Apple OS 26 expected GA. Legacy MDM update commands fully removed. Devices on OS 26+ ignore MDM update policies if DDM is enforced. Migrate now.

Quick Decision Guide
Which Method
Should You Use?
🪟
Creating a new Windows policy?
→ Settings Catalog first. Search for the setting. Only use OMA-URI if it genuinely doesn't exist in the catalog.
🍎
Managing Apple software updates?
→ DDM via Settings Catalog. Legacy MDM update commands are deprecated — OS 26 removes them entirely.
📁
Have existing Admin Template policies?
→ Keep them (they still work). But rebuild any new equivalent policies in Settings Catalog.
⚙️
Setting not in Settings Catalog?
→ Custom OMA-URI using the exact path from Microsoft's CSP reference. Double-check Device vs User scope.
